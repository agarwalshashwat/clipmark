> Status: **plan only**, no tests written yet. Scope: the launch-blocker security/payments
> paths. Companion to the coverage audit. Covers the five must-have test areas, the two
> enablers that unblock them (local Supabase in CI, DI refactor of the webapp clients), and
> a should-have appendix (manifest static test, config-guard pure-fn test).

## 0. Context & conventions

- **Runner:** reuse the native `node --test` already used by `tests/unit/*.test.mjs`. TypeScript
  test files run via the repo's existing `tsx` (`node --import tsx --test <files>`), so **no new

## Enabler (a) — Local Supabase in CI

### Goal
Give integration tests a real Postgres + GoTrue (auth) + PostgREST stack so RLS policies, column
privileges, JWT validation, and entitlement writes are exercised exactly as in production.

### One-time repo additions
1. **Commit `supabase/config.toml`** (generated by `supabase init`, then trimmed). Committing it
   (rather than running `supabase init` in CI) makes `supabase start` deterministic and pins ports.
   Keep the default local ports: API `54321`, DB `54322`, Studio `54323`.
2. **Seed script** `tests/integration/fixtures/seed.ts` (see “Fixtures / seed data” below). No new
   dependency — it uses `@supabase/supabase-js` (already present).
3. **Do NOT** use Supabase CLI’s own migration folder. Reuse the existing
   `webapp/scripts/migrate.ts`, pointing `DATABASE_URL` at the local DB. This guarantees CI applies
   the *same* migration path (incl. `schema_migrations` tracking) as production.

### Migration application in CI
```bash
# after `supabase start`
cd webapp
DATABASE_URL='postgresql://postgres:postgres@localhost:54322/postgres' \
  npx tsx scripts/migrate.ts
```
The local DB URL/keys are the well-known Supabase local defaults (stable across installs); the
service-role and anon keys can also be read programmatically with `supabase status -o json`.

### New CI job (append to `.github/workflows/ci-launch-gates.yml`)
```yaml
  integration:
    name: ci-integration
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - uses: supabase/setup-cli@v1
        with: { version: latest }
      - run: npm ci
      - run: npm --prefix webapp ci

      - name: Start local Supabase (Postgres + GoTrue + PostgREST)
        run: supabase start            # boots the Docker stack; ~1–2 min first run

      - name: Apply migrations
        working-directory: webapp
        run: DATABASE_URL='postgresql://postgres:postgres@localhost:54322/postgres' npx tsx scripts/migrate.ts

      - name: Export stack env for tests
        run: |
          echo "NEXT_PUBLIC_SUPABASE_URL=http://localhost:54321" >> "$GITHUB_ENV"
          echo "NEXT_PUBLIC_SUPABASE_ANON_KEY=$(supabase status -o json | jq -r .ANON_KEY)" >> "$GITHUB_ENV"
          echo "SUPABASE_SERVICE_ROLE_KEY=$(supabase status -o json | jq -r .SERVICE_ROLE_KEY)" >> "$GITHUB_ENV"

      - name: Seed test users
        run: node --import tsx tests/integration/fixtures/seed.ts   # idempotent; safe to re-run

      - name: Run integration tests
        env:
          DODO_PAYMENTS_WEBHOOK_SECRET: whsec_test_dummy_for_signing
          DODO_PAYMENTS_API_KEY: test_dummy
          ADMIN_USER_IDS: ${{ '' }}   # overridden per-test via seeded admin id (see #5)
        run: npm run test:integration

      - name: Stop Supabase
        if: always()
        run: supabase stop
```
Notes:
- **Caching:** first `supabase start` pulls images (~1–2 min). Optionally cache Docker layers; not
  required for correctness.
- **Determinism:** local anon/service keys are fixed demo values; still read them via
  `supabase status` so the job survives a CLI change.
- **Keep it separate** from the existing gates so a Docker/stack flake doesn’t block the fast
  `ci-unit` gate. Mark it required-for-merge once stable.

### Local dev usage (documented in the plan for contributors)
```bash
supabase start
cd webapp && DATABASE_URL='postgresql://postgres:postgres@localhost:54322/postgres' npx tsx scripts/migrate.ts
export $(supabase status -o env | sed 's/^/NEXT_PUBLIC_/' ...)   # map to the 3 env vars
node --import tsx tests/integration/fixtures/seed.ts
npm run test:integration
```

## Enabler (b) — Dependency-injection refactor (Supabase + Dodo clients)

### Problem
Route handlers construct clients at **module scope** from env
(`const supabaseAdmin = createClient(...)`, `const dodo = new DodoPayments(...)`), so unit tests
can’t substitute fakes. Next also requires the exported `POST`/`GET` signatures to stay intact.

### Shape: extract a testable core + a `deps` object with production defaults
Backward-compatible pattern — the exported route stays a thin wrapper; behavior is unchanged when
no deps are passed.

1. **New `webapp/lib/clients.ts`** — lazy, memoized factories (replaces the inline `createClient`
   in each route and the inline `dodo`):
   ```ts
   import { createClient, type SupabaseClient } from '@supabase/supabase-js';
   import DodoPayments from 'dodopayments';

   let _admin: SupabaseClient | null = null;
   export function getSupabaseAdmin(): SupabaseClient {
     return (_admin ??= createClient(
       process.env.NEXT_PUBLIC_SUPABASE_URL!,
       process.env.SUPABASE_SERVICE_ROLE_KEY!,
     ));
   }

   let _dodo: DodoPayments | null = null;
   export function getDodo(): DodoPayments {
     return (_dodo ??= new DodoPayments({
       bearerToken: process.env.DODO_PAYMENTS_API_KEY!,
       webhookKey:  process.env.DODO_PAYMENTS_WEBHOOK_SECRET!,
       environment: process.env.NODE_ENV === 'production' ? 'live_mode' : 'test_mode',
     }));
   }
   ```
   Memoization is lazy so importing a route in a unit test does **not** eagerly build a real client
   from missing env (a current footgun).

2. **Per-route: split handler core from the export.** Example for the webhook
   (`app/api/webhooks/dodo/route.ts`):
   ```ts
   export interface WebhookDeps {
     dodo: Pick<DodoPayments, 'webhooks'>;
     admin: SupabaseClient;
   }
   export async function handleDodoWebhook(request: NextRequest, deps: WebhookDeps): Promise<NextResponse> {
     /* current body, using deps.dodo / deps.admin instead of module globals */
   }
   // Next entrypoint — unchanged contract, production defaults:
   export async function POST(request: NextRequest) {
     return handleDodoWebhook(request, { dodo: getDodo(), admin: getSupabaseAdmin() });
   }
   ```

3. **Apply the same split to:**
   | File | Extract | Deps to inject |
   |---|---|---|
   | `app/api/webhooks/dodo/route.ts` | `handleDodoWebhook(req, deps)` | `dodo`, `admin` |
   | `app/api/share/route.ts` | `handleShare(req, deps)` | `admin`, `getUserId` (wraps `getAuthenticatedUserId`) |
   | `app/api/bookmarks/route.ts` | `handleGetBookmarks` / `handlePutBookmarks(req, deps)` | `admin`, `getAuthedUser` |
   | `app/api/admin/_lib.ts` | keep `requireAdmin()` but accept optional `serverClientFactory` | server client, `admin` |

4. **`getAuthenticatedUserId` / `getAuthenticatedUser`** already isolate auth — pass them in as a
   `deps.getUserId` function so unit tests inject "returns null" (unauthorized) or "returns
   `user-A`" without touching real GoTrue.

### Backward-compatibility guarantees
- Exported `POST`/`GET`/`OPTIONS` names and signatures unchanged → Next routing unaffected.
- Production default deps reproduce the exact current client construction (same env vars).
- No behavior change in prod; only new seams for tests. `lib/supabase.ts` public exports stay;
  `getSupabaseAdmin()` centralizes what was duplicated inline in 3 routes.
- **Verification for the refactor itself:** existing webapp build + typecheck must stay green;
  add a smoke assertion that `POST` still returns 401 with no auth header (unit test #3 covers it).

### Fake clients (unit tier)
- `tests/integration/fixtures/fake-supabase.ts` (also used by unit) — a chainable builder mock:
  `from().select().eq().single()` etc. return configurable `{ data, error }` and record calls, so
  a test can force an `update().eq()` to return `{ error: { message } }` (drives the 500 path).
- `tests/integration/fixtures/dodo.ts` — a fake `{ webhooks: { unwrap } }` where `unwrap` either
  throws (→401) or returns a chosen payload; plus a helper to build a real signed body if we want
  to exercise the actual `unwrap` verification.

## #1 — RLS: self-grant-Pro prevention  *(integration)*

**Files:** `tests/integration/webapp/rls-profiles.test.ts`, `rls-collections.test.ts`
**Fixtures:** seeded user A (free), user B, service-role client, anon-key client, user-A-JWT client.

### Scenarios / assertions
**profiles (column-level UPDATE allow-list — migration 012):**
- As **authenticated user A** (anon key + A’s JWT), `update({ is_pro: true }).eq('id', A)`:
  - the call is rejected **and** re-reading the row shows `is_pro` **unchanged** (assert both — a
    silently-ignored column write must not mutate state).
- Same for `is_affiliate: true`, `commission_rate: 0.9`, `is_gifted_pro: true`, `pro_payment_id`.
- **Allowed** columns still work for the owner: `update({ username, avatar_url, cancel_at_period_end })`
  on own row succeeds.
- User A **cannot** update user B’s allowed columns (row-level ownership still holds).
- **Service-role** client can set `is_pro: true` (webhook path must keep working).

**collections (migration 012):**
- **INSERT** as anon (no auth) → rejected; as authenticated A with `user_id = A` → allowed; as A
  with `user_id = B` (spoofed owner) → rejected (`WITH CHECK auth.uid() = user_id`).
- **UPDATE** of an existing collection by a non-owner (anon or user B) → rejected (the old
  `USING(true)` policy is gone; assert row unchanged).
- **`increment_collection_view(id)` RPC** as **anon** → succeeds and bumps `view_count` by exactly
  1; assert it **cannot** be abused to change any other column (it’s a fixed `UPDATE ... SET
  view_count`). Call twice → +2.

**Why:** revenue/paywall integrity + share-hijack prevention; RLS is invisible to app code, so this
is the only regression signal.

## #2 — Dodo webhook  *(unit for branches, integration for entitlements)*

**Files:** `tests/unit/webapp/webhook-dodo.test.ts`, `tests/integration/webapp/webhook-entitlements.test.ts`
**Fixtures:** fake Dodo (`unwrap` throw/return), fake Supabase (unit); real seeded profiles +
signed payload helper (integration).

### Unit scenarios (no DB — via `handleDodoWebhook(req, deps)`)
- **Signature:** headers missing/invalid → `deps.dodo.webhooks.unwrap` throws → response **401**
  `{error:'Invalid signature'}`; body is never processed.
- **500-on-write-failure:** valid `payment.succeeded`, but `deps.admin` update returns
  `{ error }` → `assertWrite` throws → response **500** `{error:'processing_failed'}` (so Dodo
  retries). Repeat for `subscription.active`, `subscription.cancelled`, `refund.succeeded` revoke.
- **Happy 200:** valid event, writes succeed → **200** `{received:true}`.
- **No user_id in metadata** → no write attempted, still 200 (assert `admin.update` not called).
- **Plan mapping:** `subscription.active` with `product_id === DODO_ANNUAL_PRODUCT_ID` → `plan:'annual'`,
  else `'monthly'` (assert the value passed to conversion recording).

### Integration scenarios (real DB)
- **refund.succeeded → revoke Pro:** seed profile with `is_pro=true, pro_payment_id='pay_X'`; deliver
  a refund for `pay_X` → row becomes `is_pro=false, pro_payment_id=null`; a matching **pending**
  `affiliate_conversions` row flips to `cancelled`.
- **payment.succeeded → grant:** `is_pro=true`, `pro_payment_id` stored.
- **Duplicate-credit guard:** deliver `payment.succeeded` for an **already-Pro** user → no second
  `affiliate_conversions` / `referrals` row; **self-referral** (affiliate_code === buyer) → no row.
- **subscription.cancelled/expired → revoke:** `is_pro=false`, `subscription_id=null`.
- **(Known gap to also cover once implemented):** webhook-id idempotency — redelivering the *same*
  `webhook-id` must not double-write. Recommend a `webhook_events(webhook_id PK)` dedup table +
  test; note it’s currently missing.

**Why:** every branch here is a direct money path (free-Pro faucet, refunded-keeps-Pro, silent
write loss, double affiliate/referral credit).

## #3 — /api/share: auth requirement + free-tier limit  *(unit + integration)*

**Files:** `tests/unit/webapp/share-auth.test.ts`, `tests/integration/webapp/share.test.ts`
**Fixtures:** `deps.getUserId` stub (unit); seeded free user with N existing collections, Pro user,
valid/invalid JWTs (integration).

### Unit scenarios (via `handleShare(req, deps)`)
- No `Authorization` header and no cookie session → `getUserId` returns null → **401**.
- Invalid Bearer token → **401**.
- **Spoof:** body includes `userId: 'victim'` but token is user A → the inserted `user_id` is **A**,
  not `'victim'` (assert the value passed to `admin.insert`). Confirms body userId is ignored.
- Bad input: missing `videoId` / empty `bookmarks` array → **400**.
- Bookmarks are **sorted by timestamp** before insert (assert ordering of the insert payload).

### Integration scenarios (real DB)
- Free user with **4** collections → share succeeds (**201**, `shareId` returned,
  `collectionsUsed` reported).
- Free user with **5** (`FREE_SHARE_LIMIT`) → **403** `free_limit_reached` with `limit`/`count`.
- **Pro** user with ≥5 → succeeds (unlimited).
- Both auth transports resolve the same identity: Bearer-token path and cookie-session path.

**Why:** closed a spoofing + paywall-bypass + anon-insert hole; regression re-opens all three.

## #4 — Cloud sync `/api/bookmarks`: RLS isolation + Pro-gate  *(integration, some unit)*

**Files:** `tests/integration/webapp/bookmarks-sync.test.ts`, `tests/unit/webapp/bookmarks-guard.test.ts`
**Fixtures:** two seeded Pro users (A, B) each with `user_bookmarks` rows, one free user, JWTs.

### Unit scenarios
- GET/PUT with no auth → **401**.
- GET/PUT as a **free** (non-Pro) user → **403** `pro_required` (assert before any DB read/write).
- PUT with missing `videoId`/non-array `bookmarks` → **400**.

### Integration scenarios (real DB + RLS via user-scoped client)
- **Isolation:** user A `GET /api/bookmarks` returns **only A’s** rows; A cannot read B’s row even
  by passing B’s `videoId` (RLS `auth.uid()` scoping via the JWT-bound client → empty/PGRST116).
- **Round-trip:** A `PUT` a video’s bookmarks → `GET` returns them; second `PUT` same
  `(user_id, videoId)` **upserts** (no duplicate row; `updated_at` advances).
- Cross-user write attempt: A cannot upsert a row that resolves to B’s `user_id` (RLS rejects).

**Why:** cross-user leakage = privacy incident; Pro-gate regression hands a paid feature to free
users.

## #5 — Admin route authorization  *(unit + integration)*

**Files:** `tests/unit/webapp/admin-auth.test.ts`, `tests/integration/webapp/admin-grant.test.ts`
**Fixtures:** seeded admin user (id placed in `ADMIN_USER_IDS`), non-admin user, target user.

### Unit scenarios (`requireAdmin` with injected server-client factory)
- No session → **401**; authenticated non-admin (id not in `ADMIN_USER_IDS`) → **403**;
  admin → passes (returns `{ userId }`).
- **Meta-test:** every route file under `app/api/admin/*/route.ts` calls `requireAdmin()` as its
  first statement (static source scan) — catches a new admin route that forgets the guard.
  Rationale: `middleware.ts` guards `/admin` **pages** but not `/api/admin/*` (path prefix
  mismatch), so in-route `requireAdmin()` is the *only* server-side guard.

### Integration scenarios (real DB)
- `POST /api/admin/grant-pro` as admin with `{ userId: target }` → target’s `is_pro=true`,
  `is_gifted_pro=true`, optional `gifted_pro_expires_at`/`gifted_by_note` applied.
- Same call as **non-admin** → **403**, and target’s `is_pro` **unchanged** (assert no write).
- `grant-pro` with missing `userId` → **400**; invalid JSON → **400**.

**Why:** these routes mint Pro/affiliate for arbitrary users — a missing guard is a
privilege-escalation faucet with no other signal.

## Appendix — Should-haves (no enablers required; land first)

### #6 — Manifest permission static test  *(unit, XS)*
**File:** `tests/unit/manifest.test.mjs` (plain `node:test`, no deps; runs inside existing `test:unit`).
Assertions against `extension/manifest.json`:
- `permissions` does **not** include `tabs`.
- `web_accessible_resources[*].matches` does **not** include `<all_urls>`; equals the youtube + app
  origin allow-list.
- `externally_connectable.matches` contains **no** `localhost`/`127.0.0.1` entry.
- `version` **equals** `extension/package.json` version (guards the 1.0 vs 1.0.0 drift we fixed).
- `host_permissions` equals the expected set.
- *(Optional extension):* after `make ext-build`, unzip `clipmark-extension.zip` and re-assert the
  built `manifest.json` — automates the manual ext-zip validation from the hardening work.

### #7 — Config build-guard pure-fn test  *(unit, XS)*
**Refactor:** extract the localhost check from `extension/vite.config.mjs` into a pure function
`extension/scripts/api-base-guard.mjs`:
```js
export function assertProdApiBase(source) {
  const m = source.match(/API_BASE\s*=\s*['"`]([^'"`]*)['"`]/);
  if (!m) throw new Error('Could not find API_BASE');
  if (/localhost|127\.0\.0\.1/i.test(m[1])) throw new Error(`API_BASE points at local dev: ${m[1]}`);
  return m[1];
}
```
`vite.config.mjs` imports and calls it inside the existing `apply:'build'` plugin (behavior
unchanged). **File:** `tests/unit/api-base-guard.test.mjs`:
- `https://clipmark.mithahara.com` → returns the URL, no throw.
- `http://localhost:3000` → throws.
- `https://127.0.0.1:3000` → throws.
- source with no `API_BASE` → throws.
- *(Optional integration):* run `vite build` in a temp dir with a localhost config, assert non-zero
  exit — heavier; the pure-fn test covers the logic cheaply.
